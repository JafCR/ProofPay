# DECISIONS.md · ProofPay

Registro de desviaciones del spec y decisiones de arquitectura tomadas durante el build.
Una línea por decisión: fecha, qué, por qué. Se lee al inicio de cada sesión de desarrollo.

- 2026-08-24 · Repo creado. Spec v1.0 adoptado como fuente de verdad (docs/SPEC.md).
- 2026-08-25 · Fraude reencuadrado v2 — "registry drift/revocación" (sustituye v1; CONTRACTS.md §9 n.4 + hallazgo: reject solo es legal desde submitted en TRANSITIONS de Pacta, y el registry adapter es pluggable): demo-fraud = provider-bot MODE=fraud intenta la ref forjada (Pacta la bloquea con 409, evidencia capa 1), cae a refs válidas, completa y SUBMITea sin notificar; demo_fraud.sh revoca un registry record (DELETE en registry_records de data/pacta.db — data runtime, no código Pacta) y dispara el evento delivery; el agente re-verifica TODAS las refs en Wake-2, obtiene 404 en la revocada → P2 falla → DISPUTE con reject legal desde submitted. La re-verificación independiente del agente es load-bearing: la plataforma verificó al submit, el agente re-verifica al mover dinero. Phase B: revocación remota vía REGISTRY_URL apuntando a un mini registry service propio (adapter http oficial de Pacta) — decidir en Phase B. [PENDIENTE VETO JAF]
- 2026-08-25 · Slashing (CONTRACTS.md §9 n.2): reject_and_open_dispute no slashea; el slash ocurre solo en POST /resolve (árbitro, sin tool MCP). demo_fraud.sh juega el rol de árbitro vía REST (ruling=refund, 20% del precio) e imprime stake antes/después (150000→50000 verificado). El agente nunca llama /resolve. [PENDIENTE VETO JAF]
- 2026-08-25 · P5 numérico (CONTRACTS.md §9 n.3): MCP devuelve montos como strings ("$5,000"); para P5 el agente lee además GET /engagements/:id por REST (escrow_balance_cents etc.) como telemetría de solo lectura. Todas las MUTACIONES siguen siendo exclusivamente vía MCP sin modificar. [PENDIENTE VETO JAF]
- 2026-08-25 · Verdicto WAIT (final, reconcilia SPEC §3 "no third outcome" con §4): policy.evaluate(mission, checks, engagement) devuelve SOLO RELEASE|DISPUTE. WAIT lo registra la orquestación ANTES de correr el gate, cuando el engagement aún no está submitted (Pacta exige todos los steps done para submit) y el deadline de entrega sigue vigente; vencido el deadline sin entrega, la orquestación SÍ corre el gate y P1 falla → DISPUTE. RELEASE solo puede salir de policy.evaluate; WAIT jamás libera fondos. Montos de EngagementInfo en cents (campos escrow_balance/release_amount, unidad documentada en el modelo; release_amount = upfront_cents del REST de Pacta). Nota: un dispute por no-entrega no puede mover el engagement Pacta a disputed (reject exige submitted); se registra localmente y la escalación al árbitro queda manual/fuera de scope. [PENDIENTE VETO JAF — semántica de policy.py]
- 2026-08-25 · P5 = escrow_balance_cents >= upfront_cents: en Pacta el escrow retiene solo el upfront (el remaining se cobra en approve); la lectura literal "escrow >= precio" rompería todo happy path. Detecta escrow drenado sin falsos positivos. [PENDIENTE VETO JAF — semántica de policy.py]
- 2026-08-25 · P1 endurecido: un engagement con CERO steps evalúa a DISPUTE (P1), no a release vacuo. Aditivo hacia la seguridad. [PENDIENTE VETO JAF — semántica de policy.py]
- 2026-08-25 · Selección con presupuesto duro: judge.select_offer recibe budget_usd y una oferta con precio sobre el presupuesto no puede ganar (stub la filtra; el prompt Gemini lo declara como regla dura). Sin esto el stub elegía la oferta de $300k por tener el mayor colateral. Además, si el goal narrativo no matchea la búsqueda por keywords de Pacta, el adapter amplía al catálogo completo y deja la selección al judge.
- 2026-08-25 · Phase B, vía de modelo elegida (SPEC §5 pedía UNA): Vertex AI con ADC (sin API key en archivos); GEMINI_MODEL pinneado a `gemini-3.5-flash`, verificado contra la lista real de modelos del proyecto optimal-signer-506615-d5 (location `global`) con una generación estructurada de prueba exitosa.
- 2026-08-25 · Settings nuevos para la vía Vertex: GOOGLE_CLOUD_LOCATION (default global) y STATE_BACKEND (auto|memory|firestore, default auto = Firestore sii hay project). "memory" permite correr demos locales con el judge Vertex (que exige project) sin arrastrar Firestore. Judge calibrado contra Gemini real: los 3 prompts consistentes en 3 corridas (incl. resistencia a prompt injection); ambos demos verdes con juez real (happy RELEASED, fraud DISPUTED P2 con dispute reason redactado por Gemini).
- 2026-08-25 · Verify fail-closed: el MCP de Pacta reporta el 404 de verify_registry_reference como texto plano SIN isError (verificado empíricamente); el adapter recupera el status del texto y ante un payload ininterpretable devuelve "no verificado" — un record ilegible jamás cuenta como verificado.
- 2026-08-25 · Montos en la interfaz del gate en CENTS (int, de los *_cents del REST de Pacta), no USD: evita pérdida de precisión y parseo de strings.
- 2026-08-25 · wait_for_provider_submission (tool MCP bloqueante) queda prohibido en el agente: contradice el diseño async "el agente duerme" (CONTRACTS.md §9 n.5).
- 2026-08-25 · Infra Phase B (T15, escrita sin ejecutar): (a) registry-drift/ = mini servicio node sin deps que implementa el contrato http del adapter de Pacta y expone POST /revoke/:ref (guard REVOKE_TOKEN) para el fraude en cloud — verificado localmente: marketplace con REGISTRY_URL→drift da 200 en /complete con ref válida y 404 tras revoke. (b) marketplace usa node:24-alpine (NO node:22): Pacta persiste con `node:sqlite` (DatabaseSync), que corre sin flag solo en Node ≥23; coincide con el Dockerfile propio de Pacta. Pin del clon vía PACTA_COMMIT=2ce2abe1. (c) agent image = node:22-bookworm-slim + python3.11 (bookworm), instala `.[google]` (el extra ya incluye genai+adk+firestore). (d) provider-bot se despliega como Cloud Run **Job** (es worker, no sirve puerto); bot.js gana PUBSUB_TOPIC (publica a Pub/Sub vía import dinámico, con fallback HTTP intacto). (e) agent Cloud Run --allow-unauthenticated pero el push sub y Scheduler se configuran igual con OIDC (invoker SA) para forma prod. Todos los deploy.sh son write-only y hacen echo de cada gcloud antes de ejecutarlo.
