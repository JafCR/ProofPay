# DECISIONS.md · ProofPay

Log of spec deviations and architecture decisions made during the build.
One line per decision: date, what, why. Read at the start of every development session.

- 2026-08-24 · Repo created. Spec v1.0 adopted as the source of truth (docs/SPEC.md).
- 2026-08-25 · Fraud reframed as v2, "registry drift / revocation" (replaces v1; CONTRACTS.md §9 n.4 plus a finding: reject is only legal from submitted in Pacta's TRANSITIONS, and the registry adapter is pluggable): demo-fraud = provider-bot MODE=fraud attempts the forged ref (Pacta blocks it with a 409, layer 1 evidence), falls back to valid refs, completes and SUBMITS without notifying; demo_fraud.sh revokes a registry record (a DELETE against registry_records in data/pacta.db, runtime data only, never Pacta code) and fires the delivery event; the agent re-verifies ALL refs in Wake 2, gets a 404 on the revoked one → P2 fails → DISPUTE with a legal reject from submitted. The agent's independent re-verification is load-bearing: the platform verified at submit time, the agent re-verifies at the moment money moves. Phase B does the remote revocation via REGISTRY_URL pointing at a small registry service of our own (Pacta's official http adapter contract).
- 2026-08-25 · Slashing (CONTRACTS.md §9 n.2): reject_and_open_dispute does not slash; the slash happens only on POST /resolve (arbiter only, no MCP tool). demo_fraud.sh plays the arbiter role over REST (ruling=refund, 20% of price) and prints the stake before/after (150000→50000 verified). The agent never calls /resolve.
- 2026-08-25 · Numeric P5 (CONTRACTS.md §9 n.3): MCP returns money as strings ("$5,000"); for P5 the agent additionally reads GET /engagements/:id over REST (escrow_balance_cents etc.) as read-only telemetry. ALL mutations still go exclusively through the unmodified MCP server.
- 2026-08-25 · WAIT verdict (final, reconciles SPEC §3 "no third outcome" with §4): policy.evaluate(mission, checks, engagement) returns ONLY RELEASE|DISPUTE. WAIT is recorded by the orchestration layer BEFORE the gate runs, when the engagement is not yet submitted (Pacta requires every step done to submit) and the delivery deadline still holds; past the deadline with no delivery, the orchestration DOES run the gate and P1 fails → DISPUTE. RELEASE can only come out of policy.evaluate; WAIT never moves funds. EngagementInfo amounts are integer cents (escrow_balance/release_amount fields, unit documented on the model; release_amount = upfront_cents from Pacta's REST). Note: a non-delivery dispute cannot move the Pacta engagement to disputed (reject requires submitted); it is recorded locally and arbiter escalation stays manual / out of scope.
- 2026-08-25 · P5 = escrow_balance_cents >= upfront_cents: in Pacta the escrow only ever holds the upfront (the remainder is drawn at approve); a literal "escrow >= price" reading would dispute every happy path. This detects a drained escrow with no false positives.
- 2026-08-25 · P1 hardened: an engagement with ZERO steps evaluates to DISPUTE (P1), never a vacuous release. Additive toward safety.
- 2026-08-25 · Hard-budget selection: judge.select_offer receives budget_usd and an offer priced above the budget cannot win (the stub filters it; the Gemini prompt states it as a hard rule). Without this the stub picked the $300k offer for having the largest collateral. Also, when a narrative goal does not match Pacta's keyword search, the adapter widens to the full catalog and leaves the choice to the judge.
- 2026-08-25 · Phase B model path (SPEC §5 asked for ONE): Vertex AI with ADC (no API key in files); GEMINI_MODEL pinned to `gemini-3.5-flash`, verified against the project's live model list (location `global`) with a successful structured-output probe.
- 2026-08-25 · New settings for the Vertex path: GOOGLE_CLOUD_LOCATION (default global) and STATE_BACKEND (auto|memory|firestore, default auto = Firestore iff a project is configured). "memory" allows local demos with the Vertex judge (which requires a project) without dragging in Firestore. Judge calibrated against real Gemini: all three prompts consistent across three runs (including prompt-injection resistance); both demos green with the real judge (happy RELEASED, fraud DISPUTED P2 with a Gemini-written dispute reason).
- 2026-08-25 · Verify fail-closed: Pacta's MCP reports the verify_registry_reference 404 as plain text WITHOUT isError (verified empirically); the adapter recovers the status from the text and, on an uninterpretable payload, returns "not verified": an unreadable record never counts as verified.
- 2026-08-25 · Gate-interface amounts in CENTS (int, from Pacta's REST *_cents fields), not USD: avoids precision loss and string parsing.
- 2026-08-25 · wait_for_provider_submission (blocking MCP tool) is banned in the agent: it contradicts the async "the agent sleeps" design (CONTRACTS.md §9 n.5).
- 2026-08-25 · Phase B infra (written before executing): (a) registry-drift/ = a dependency-free node service implementing Pacta's http registry adapter contract, exposing POST /revoke/:ref (guarded by REVOKE_TOKEN) for the cloud fraud demo; verified locally: the marketplace with REGISTRY_URL→drift returns 200 on /complete with a valid ref and 404 after a revoke. (b) marketplace image uses node:24-alpine (NOT node:22): Pacta persists via `node:sqlite` (DatabaseSync), which runs unflagged only on Node ≥23, matching Pacta's own Dockerfile; the clone is pinned via PACTA_COMMIT=2ce2abe1. (c) agent image = node:22-bookworm-slim + python3.11, installing `.[google]` (the extra already includes genai+adk+firestore). (d) provider-bot ships as a Cloud Run Job (it is a worker, it serves no port); bot.js gains PUBSUB_TOPIC (publishes to Pub/Sub via dynamic import, HTTP fallback intact). (e) the agent service is --allow-unauthenticated, but the push subscription and Scheduler are still wired with OIDC (invoker SA) for production shape. All deploy.sh scripts are write-only and echo every gcloud command before running it.
- 2026-08-25 · Phase B deployed (with operator approval): 4 services live on Cloud Run us-central1 plus the OIDC push subscription and the /sweep Scheduler. Ops applied along the way: standard build grants to the default Compute SA (storage.objectViewer, logging.logWriter, artifactregistry.writer), a PROJECT-level override of iam.allowedPolicyMemberDomains (allowAll; the org policy blocked the public access judges need), and dedicated SAs assigned to the agent service and the provider job (the initial deploy ran as the default SA → Firestore 403). Both demos green IN PRODUCTION: happy RELEASED and fraud DISPUTED ['P2'] with the 150000→50000 slash; Wake 1 and Wake 2 visible as separate requests in the Cloud Run logs.
- 2026-08-25 · Self-serve demo (operator feedback: the trace page was just a textbox): a "Start a demo mission" button on web/index.html (POST /missions, then follows the trace live) plus the provider-bot ALSO deployed as an always-on service (proofpay-provider-svc, min-instances=1, MODE=honest, delivery via real Pub/Sub) so any mission created from the page completes on its own. Verified in prod: a button-flow mission ended RELEASED with the delivery traveling through Pub/Sub → OIDC push. demo_fraud.sh now restores the revoked ref on exit (a forgotten revocation poisoned later happy runs; it happened and was fixed).
- 2026-08-25 · Demo UI v2 (an 11-point operator request): home with TWO launchable missions (the law firm with registry proofs plus the Tico Adventures eco-tour without registry, both from Pacta's untouched seed), a "Your missions" pinboard in localStorage with 2-line TLDRs, a curated finished-missions section (happy/fraud/composite, real production ids) each with a short narrative story, a "How ProofPay works" walkthrough (Discover/Contract/Deliver/Verify/Settle with who runs each step), and logo → home with clean state. A freshly created Wake 1 replays step by step on the page (discover → offers → contract → escrow → sleep) over the real recorded data; it is presentation only and changes no orchestration.
- 2026-08-25 · Demo wait tuned to ~45s (provider-svc DELAY_SECONDS=45) with a visible disclaimer in the trace; the page also fires ONE real /sweep mid-wait for a freshly created mission, so the trace shows at least 3 wakes (create, sweep→WAIT, pubsub→settle) with unchanged semantics (the sweep is the same endpoint Cloud Scheduler already hits).
- 2026-08-25 · mission.offers_considered: a display snapshot of every offer the judge weighed (name, price, vetted, collateral, rating, chosen) saved in Wake 1 for the trace cards; the gate never reads it.
- 2026-08-25 · Composite missions (deviation: the SPEC models 1 mission = 1 engagement): POST /missions/composite creates a coordinating parent plus N normal child missions (each with its own engagement, escrow and wakes); the parent's status is DERIVED at read time (DISPUTED if any child disputes, RELEASED only when all release) and never persisted, so the state machine in state.py stays intact and the sweep ignores the parent. policy.py is unchanged: every child passes through the same gate as always.
- 2026-08-25 · provider-bot accepts SMB_ID as a comma-separated list (prod: "1,3" = Bufete + Tico Adventures) to serve the eco-tour mission; the default stays 1.
- 2026-08-25 · House style rule: zero em-dashes across the repo (code, docs, UI strings and logs); a full sweep was applied.
- 2026-08-25 · Curated production run (UI v2): happy 6d81574d (Tamarindo restaurant, RELEASED), fraud 76335c19 (Puntarenas marina, DISPUTED P2 with a Gemini-written dispute reason; the provider side was driven manually over REST with the revoke BEFORE the submit so not even a Scheduler sweep could release inside the window), composite c18d50e7 (Bufete + Tico, RELEASED). Shared-marketplace hygiene: SMB 1's stake was normalized to 150000 cents via POST /smbs/1/stake (a public Pacta endpoint, simulated deposit) before and after the arbiter slash (150000→50000), because vetted ⇔ stake>0 and a zeroed stake would have un-vetted the firm and broken the live demos. The revoked ref was restored; drift health shows revoked=[]. Verified E2E in prod: the hotel button mission ended RELEASED with 3 real wakes (create, sweep→WAIT at ~23s, pubsub→RELEASE) and the eco-tour run had Gemini pick Tico Adventures and release.
- 2026-08-25 · Long-run mission for the demo video: a mission was launched against LexCorp (SMB 2, which no always-on bot serves) so the agent genuinely sleeps for ~36 hours; delivery is triggered by a one-off Cloud Scheduler entry (proofpay-longrun-delivery, Aug 27 09:00 UTC) executing the provider job repointed at SMB 2, with a local fallback script an hour later. DELIVERY_DEADLINE_SECONDS was raised to 259200 (72h) so the sweep cannot deadline-dispute the sleeping mission, and the /sweep Scheduler cadence moved from every 10 minutes to every 6 hours so the long trace shows a handful of meaningful WAIT wakes instead of ~200.
- 2026-08-27 · Incident and fix: the first long-run mission auto-disputed at the 24h mark because later agent deploys reset DELIVERY_DEADLINE_SECONDS to the deploy script's 86400 default, clobbering the 259200 override set directly on the service (P1 correctly disputed an undelivered engagement past its deadline; the gate worked as designed, the config did not). Fix: deploy.sh default raised to 259200 so redeploys keep the long window, the service env restored, and a replacement long-run mission launched with delivery rescheduled ~36h out. Lesson recorded: env set with gcloud services update does not survive a deploy that passes --set-env-vars.
- 2026-08-28 · Long-run delivery incident and fix (RELEASED after 10 wakes, 40.1h wall clock). The 15:00 UTC scheduled delivery landed on phantom engagement #15: the agree/fund for #16 recorded on the 27th never actually applied on the marketplace (LexCorp's exposure cap was still occupied by #15), and the orchestrator logged ok:true without reading the MCP's error payload. On top of that the demo economy was drained: the agent had $1,050 left of the $50,000 seed after ~18 demo missions, which stranded a visitor mission (engagement 17) in submitted. Fix (approved by Jaf): bounced the marketplace for a fresh re-seeded economy, recreated the engagement off the same offer 2 (it was born as id 1), and re-pointed the mission's engagement_id "16"→"1" in Firestore (an ops repair; the seam is left visible in the trace on purpose). The re-delivery Pub/Sub event was then absorbed by the Aug-25 demo mission that also carried engagement_id "1" (a collision in engagement-based resolution), so the final settle was done by a hand-fired /sweep at 19:36 UTC. Lessons: (a) surface MCP tool errors in Wake 1 instead of logging ok, (b) delivery events need a mission_id or unique engagement ids, (c) a perpetual public demo economy needs a top-up mechanism.
- 2026-08-29 · Provider reliability fix: proofpay-provider-svc ran with Cloud Run's default CPU throttling, so its polling loop froze whenever no HTTP traffic arrived (min-instances=1 keeps the instance alive but not its CPU) — deliveries were intermittently stuck until some request woke it. Fixed with --no-cpu-throttling (+ --memory 512Mi, required by that mode). Deliveries now land consistently ~50s after funding.
